# Ability.Core 项目规格

Core 为 Sdk 与 Hosting 提供共享契约、通信组件和校验能力。内部组织见 [architecture.md](architecture.md)；帧格式、大小限制、握手和结果语义引用[全局接入方案](../../../Docs/技能接入协议与SDK方案.md)第五至七节。

## 一、共享接口与类型

| 接口或类型 | 调用契约 |
| --- | --- |
| `IpcEnvelope` 与消息体 | 表达线协议数据；业务载荷保持 JSON，引用型资源保持字符串 |
| `ProtocolMessages` | 构造和读取已支持的消息，封装内部源生成序列化上下文 |
| `IpcFrame` | 校验、计量、编码与读写完整帧；计量和发送采用同一配置 |
| `IpcConnection` | 公开实现 `IAsyncDisposable`，在给定双工 Stream 上收发消息、匹配请求并报告断连；异步释放结束所属循环 |
| `JsonSchemaValidator` | 解析并复用 Schema，以实例 JSON 返回校验结果 |
| `DiagnosticRecord` | 跨进程共享结构化诊断契约，解耦日志/追踪收集与宿主导出 |
| 协议及校验异常 | 区分本地发送拒绝、连接损坏、定义不受支持、实例违规与校验未完成 |

消息工厂和编码接口使用 Core 自身的类型元数据；泛型业务编码接收调用方提供的 `JsonTypeInfo<T>`。序列化上下文 `ProtocolJsonContext` 为内部实现，公开接口可在另外一个程序集中直接调用：
- `ProtocolMessages.ReadBody<T>(envelope)` / `ReadBody<T>(envelope, JsonTypeInfo<T>)`：按内置元数据或调用方显式提供的类型元数据解析已知协议体与泛型业务载荷（模型、DTO 等纯数据结果）。
- `IpcFrame.EncodeFrame(envelope)`：分配并返回包含 4 字节小端前缀与 UTF-8 JSON 的完整新帧。通用编码与发送校验路径必须在有限工作空间内执行，超限（载荷超 1 MiB、载荷工作空间超 6 MiB + 16、整帧超 16 MiB 或整帧工作空间超 128 MiB）立即拒绝并抛出 `PayloadTooLargeException`，杜绝无界内存分配；信封输出上限（16 MiB，`MaxEnvelopeBytes`）与信封工作空间上限（128 MiB，`MaxEnvelopeWorkspaceBytes`）分别明确定义，工作空间上限依据 `Utf8JsonWriter` 源码中写入转义属性/值时的最坏暂存申请规则严格推导（`sizeHint = 6 * L + 4` 覆盖引号、冒号与前置逗号开销，`W + 6 * L + 4 <= 96 MiB + 4`，加上信封结构与缓冲扩容二进制翻倍对齐裕量），杜绝写出器在包含大比例转义字符时申请大于提交量导致的误拒；针对已解析的结构化 JSON 载荷提供基于 `Utf8JsonReader` 的低成本迭代 Token 扫描，允许尾逗号并跳过注释以兼容合法已解析值的多种原始字节表现（线协议入站解析规则保持现状），与写出器共享默认容器深度上限（1000），避免创建与 Token 长度等比的中间字符串，扫描状态受深度上限约束且避免调用栈随输入深度增长；属性名与字符串值共用反转义长度判定逻辑，杜绝转义属性名误判超限，深度超限由既有反序列化异常表达，大小超限由 `PayloadTooLargeException` 表达；`BoundedBufferWriter` 保持内部类，Hosting 与 Sdk 统一调用 Core 集中导出的 `IpcFrame.ValidateJsonElementBounded` 与 `IpcFrame.ValidateStringPayloadBounded` 进行有界校验；实际线协议以线上传输的 UTF-8 字节数为权威依据：泛型业务载荷（模型、DTO 等纯数据结果）快速编码遵守业务方提供的 `JsonTypeInfo<T>`（含其配置的编码器）；通用信封编码与公开计量采用一致的线写出器选项；入站校验时，结构化载荷以及 `ParamValue` 的文本载荷严格以收到的线协议原始切片/Token 实际物理字节数（含双引号与转义）为依据核验（<= 1 MiB），精准拦截网络线缆超限载荷（如转义后达 1.2 MB），同时接纳合法宽松编码载荷（如约 600 KB 中文）；出站校验保留低成本 Token 前置检查，并严格按通用写出配置的实际编码结果及有界工作空间判定物理上限，绝不因原始转义（如 180,000 个 `\u0061` 属性名）、格式空白或注释导致预拒绝；公开计量接口（`CountingBufferWriter`）按 `IBufferWriter` 契约提供空间并继续如实返回超限数据的真实大小。一元结果与流元素仅承载符合序列化与 IPC 契约的数据结果，网络句柄和外部资源保留在生产进程内部。区分进程内具名元组与 IPC 输出：入口可按内聚语义组装 DTO；直接交付其他结果类型必须有对应元数据和序列化证据，不得承诺任意元组、任意类型或任意字段配置都能完整往返。Core 内部协议信封、消息体及诊断契约属于基础设施，按职责组织在 Core 项目中，不机械套用业务 DTO 的命名与共址规则。
- 所有完整信封编码路径（包括快捷业务帧和内嵌 `ChildMessage` / `ChildMessageReply`）须在返回帧前核验最终 JSON 的完整嵌套深度不超过入站 `ReadAsync` 的默认上限 64；超深帧在本地编码阶段拒绝，避免发送后由同一协议读取器判为非法。该整信封深度检查独立于业务载荷的 1000 层 Token 前置扫描上限，不改变公开载荷计量结果。
- `IpcFrame.WriteAsync(stream, envelope, ct)`：校验并写出完整帧并立即 Flush。
- `IpcFrame.EncodeTaskInputFrame<TInput>(taskId, taskTempPath, payloadType, input, jsonTypeInfo, traceParent, traceState)`：在启动子进程前准备并返回完整 TaskInput 帧。首遍使用调用方 `JsonTypeInfo<TInput>`、编码器和转换器，以紧凑格式写入独立的 16 MiB 输出上限与 128 MiB 工作区；解析后由通用默认编码器重写载荷，并通过 `EncodeFrame` 执行最终 1 MiB 业务载荷与 16 MiB 信封校验。该首遍上限属于准备过程的有限空间约束，不是线上载荷限制；自定义转换器产生超过 16 MiB 的中间 JSON，即使归一化后较小，也会因准备空间不足而拒绝。`JsonElement.WriteTo` 会去除原始空白与注释表示。W3C `traceparent` 与 `tracestate` 纳入实际信封编码。调用方持有返回的新帧字节；Core 不公开中间缓冲。
- `JsonSchemaValidator.For(schema)` / `Parse(schema)` / `Validate(instance)`：解析并执行 Schema 校验；正则超时或实例数值超出 1000 指数绝对值上限时报告 `SchemaValidationIncompleteException`。


`IpcConnection` 提供发送、请求答复、接收消息与关闭能力。发送可标明控制或结果用途，请求可指定允许的答复类型和取消信号。接收端交付需要上层处理的消息；已匹配答复由请求等待者取得。匹配器根据消息性质和预期答复判定，带 `id` 的消息不等同于新请求。

连接创建成功后接管传入的 Stream，创建失败时由调用方释放。发送成功表示完整帧已写出，请求成功表示已取得匹配答复。取消等待后，帧是否已写出仍由连接记录，调用方据此处理可能迟到的答复。关闭结束未决请求与结果流额度等待，并中止底层 I/O；额度等待因连接关闭收到连接结束错误，不能表现为调用方取消。连接保留终止原因；循环、额度等待者和帧的实际退出及释放由连接统一负责。

公开释放契约须区分发起关闭与实际收尾完成，后者通过 `WaitClosedAsync` 核对；上层按此事实安排仍依赖连接的资源清理。

上层通过有界接收通道取得待处理消息。答复匹配和停止信号的处理保持独立于耗时业务；上层积压达到限制时明确报告失败，避免接收循环等待业务腾出空间。具体接口签名、容量和关闭期限在连接组件实施时补入本节。

## 二、线协议实施约定

通用消息及字段以全局方案为准。以下补充项目实施约定，JSON 字段采用 camelCase，可选空字段省略。消息字段、默认值及请求答复关系在契约迁移时核实并补齐。

| 项目 | 实施约定 |
| --- | --- |
| 请求编号 | 使用 `long`，由所在连接唯一的单调自增生成器统一分配（`RequestMatcher.NextRequestId()` 经 `IpcConnection.NextRequestId()` 暴露）；禁止在上层会话或子调用维护独立序号源以免同一连接请求撞号；转发分别保存内外请求的匹配关系 |
| `optionalNotification` | 仅用于无 `id` 的通知；未知类型置为 true 时可忽略，带 `id` 时该组合无效 |
| `Hello` 扩展 | 增加 `resultCreditWindow`、`cleanupGracePeriod`、`buildTimeout`、`connectionTimeout`；时间跨度按 System.Text.Json 的 TimeSpan 字符串格式表示 |
| `ParamRequest` 扩展 | 可选 `payloadType` 表示期望的结构化答复类型 |
| `ParamValue` | 字符串 `value` 与 `payloadType`＋`payload` 互斥；判定并校验实际发送形态 |
| 运行策略字段 | v3 保留 `maxAttempts`，含首次尝试；公开重试上限映射为 `maxAttempts = maxRetries + 1`，转换前检查范围 |
| 内层载荷 | `ChildMessage.message`、`ChildMessageReply.response` 递归使用完整信封校验，内层业务载荷同样受限 |

子调用和操作的补充消息如下。请求及答复带原关联 `id`，通知按消息性质处理。

| 消息 | 消息体与用途 |
| --- | --- |
| `ChildStart` → `ChildStarted` | 请求含 `invocationKey`、`parentInvocationKey`、`taskId`、`launcherPath`；答复确认调用键、任务及实际进程号 |
| `ChildStop` → `ChildReaped` | 停止请求含调用键、父调用键及原因；回收答复含实际退出码、回收状态、剩余租约清理数及是否自然退出 |
| `ChildMessage` → `ChildMessageReply` | 按调用键转发内层信封；答复的 `response` 可空，表示无内层答复 |
| `ChildControl`（工厂方法） | 便捷构造宿主控制通知；线协议上统一作为无外层 `id` 的 `ChildMessage` 传输与路由 |
| `SourceRepair` → `SourceRepairResult` | 请求含来源种类、引用、失败类别及是否可热更新；结果为 `Reread`、`RestartRequired`、`Denied`、`Cancelled` |
| `OperationStarted`、`AttemptEnded`、`OperationEnd` | 记录操作键、累计尝试数、状态及原因；分别表达尝试开始、尝试结束和操作结束 |
| `OperationExpired` | 记录操作键、策略版本、来源及到期动作 |
| `ResultClose` → `ResultClosed` | 技能端发送无体 `ResultClose` 声明流结束；宿主回发 `ResultClosed(itemCount)` 确认接收总数完成对账并关闭结果流 |

调用键、操作键及请求编号分别校验归属。消息名称与字段属于线协议，程序集改名由上层 API 单独处理。

框架沿用 v3 的既有通信格式。公开类型改名保持字段名称、值含义和消息关联方式兼容；可选扩展应明确缺省行为。`RequestFault` 保留 `kind` 与 `message`，请求发生的位置由接收端结合本地调用信息记录。诊断记录契约与 IPC 信封分别定义和演进。

## 三、通信组件约束与共享连接

Core 提供双工通信底座，将底层帧读写、出站调度与请求匹配组合为共享连接组件 `IpcConnection`。Sdk 与 Hosting 均通过本组件管理已建立的流。

### 1. 连接契约与终止语义

| 类型／成员 | 契约与职责 |
| --- | --- |
| `IpcConnection` | 接管已建立的双工 `Stream`，协调收发循环与生命周期 |
| `SendAsync` | 发送单向通知或内层转发帧；取得名额后排入出站队列并由写循环写出；若连接未启动则抛出 `InvalidOperationException` |
| `RequestAsync` | 发送请求并异步等待对应答复；发送前先登记等待者，收到答复、取消或断连时结束等待；若连接未启动则抛出 `InvalidOperationException` |
| `CloseAsync` | 显式发起连接关闭，在指定时限内完整覆盖出站写出排空、取消回调触发、通道/队列关闭、底层流处置与后台循环退出的全流程收尾；超时直接返回（不抛出 `TimeoutException`）并允许内部收尾在后台继续受管执行，杜绝在调用线程同步阻塞导致超时失控 |
| `WaitClosedAsync` | 等待连接收尾彻底完成并返回最终的终止原因与退出事实 |
| `Inbound` | 接收循环将入站信封投递给上层消费的 `ChannelReader<IpcEnvelope>`；通道容量有界且必须与流式信用额度及控制名额严格对齐（至少为 `initialCreditWindow + maxControlFrames + 64`，缺省 128），确保已获额度内的合法结果生产与控制消息绝不因容量瓶颈被误判为协议违规 |
| `LateReplies` / `LateReplyHandler` | 迟到答复消费模式（二选一互斥）：首次读取属性或设置回调即锁定消费模式，禁止后续混用；单消费者负责排空通道 |

连接终止原因由 `IpcTerminationReason` 明确分类：
- `NormalClosed`：正常协商完成后的优雅收尾。
- `CallerCancelled`：本地调用方主动取消操作。
- `PeerStopped`：对端主动发送停止或干净关闭管道。
- `Disconnected`：底层数据流中途遭遇意外断开（非预期 EOF 或 I/O 错误）。
- `ProtocolCorrupted`：帧长度超限、载荷非法、信封结构违规或反序列化失败导致的连接损坏。

读循环与统一终止都按固定步骤执行，调用方顺读即可看出顺序。读循环对每一帧依次执行四步：读取帧；请求匹配与迟到答复投递；结果流前置判定；投递到入站通道。读取异常在此裁决终止原因：已终止状态下的取消与流错误归为正常关闭，对端 EOF 归为对端停止，协议与载荷错误归为协议损坏，其余错误归为意外断开；任一步骤裁决终止即结束循环。统一终止依次执行：释放启动屏障；解析终止异常；结束结果流额度等待与未决请求、关闭入站与迟到答复通道并停止出站队列；启动取消回调的独立任务；处置底层流；汇聚等待循环任务、取消任务、出站队列与额度等待的实际退出；最后发布终止原因。该顺序保证失败通知先于可能阻塞的外部取消回调，取消任务先于流处置启动。开始终止时停止接纳新工作，`WaitClosedAsync` 的完成信号在上述工作实际退出后发布。

### 2. 容量配置与调度规则

- **出站容量与名额所有权**：控制队列容量可配置（缺省为 64，`MaxPendingControlFrames = 64`），结果队列上限固定为 4（`MaxPendingResultFrames = 4`）。发送方必须先取得名额信号量才允许分配缓冲并编码完整帧；名额由帧对象持有，仅在帧实际写出、跳过或丢弃后归还。在入队与停止竞争中，名额计数与释放严格一致，调用方取消等待不能提前释放仍在队列中的名额。逐条核验帧写出、取消、跳过、编码失败和连接终止路径：每个已登记帧都必须完成等待，并且只归还一次容量名额。写任务在登记时明确已被安排；仅在确实未安排写任务时才执行未启动排空路径，已安排的任务必须实际退出后才允许释放其使用的同步对象，保持调用方有限等待的语义。
- **单一写入循环与控制优先**：出站队列共用唯一的后台写入循环。调度器保障控制帧具备及时的写入机会，同时保证流式结果元素严格保序，且流关闭通知绝不跃过尚未写出的结果帧。写循环对控制帧采用单批次 8 帧上限，防止流式结果帧饥饿。
- **请求匹配与迟到答复**：请求匹配器严格基于原子状态流转（`Registered` → `Sent` → `Completed` / `Cancelled` / `Aborted` / `LateReplyHandled`），在发送前原子检查并占用未决容量（上限 64）。尚未开始写出时收到的答复明确作为协议错误（`ProtocolCorrupted`）处理，严禁在 `Registered` 状态下完成请求；写出开始后保留正常答复与取消之间的原子裁决。写入前取消原子迁移至 `Aborted` 并彻底清理，不留孤儿记录；写入开始后发生的取消标记为 `Cancelled` 并保留迟到答复处理责任。发送等待失败（取消或写入异常）的处理收回请求状态机统一原子裁决：已裁决为 `Completed` 时等待答复发布并返回结果，尚未裁决时原子提交取消或发送失败并抛出对应异常。每个 `TrackedRequest` 创建完成源时须登记静态故障观察延续，以覆盖发送失败已由 `RequestAsync` 直接抛出而完成源无人等待的路径；观察延续仅读取故障信息，不替代调用方原异常传播。迟到答复支持专用通道读取或回调单消费者处理（二选一互斥模式），通道容量 64，满溢时作为协议损坏处理，严禁静默丢弃。
- **结果流状态与信用额度**：结果流组件管理流状态（`None` → `Open` → `Closed` / `Faulted`）。在收到流元素的底层协议读循环阶段核验当时有效额度（超出立即判定协议损坏），与后续上层业务消费、归还额度分别记录；技能端流式枚举必须在生产前先获取信用额度，未产出项时归还额度；技能端发送无体 `ResultClose` 请求关闭，宿主核验实际接收计数后回发 `ResultClosed(itemCount)` 完成对账并关闭结果流。默认额度等待由结果流状态管理器登记所有者；显式 Dispose 或所属连接终止会停止并结束已登记等待，关闭后拒绝新等待。状态管理器仅在停止取消工作已返回且全部额度使用者实际退出后释放信号量与内部取消源；连接把额度等待退出纳入 `WaitClosedAsync`，保留已记录的流计数。调用方取消仍按调用方令牌传播。根连接的流校验与计数集中在 `ResultStreamState`，子连接的结果校验与剩余额度集中在 `ChildSession`。简单状态比较直接使用各端已有字段，不设置跨程序集的布尔判定工具；各端保留自己的消费确认时机、关闭比对对象、错误消息及一元与故障终态接纳规则。
- **接收独立性、协议校验与资源释放**：接收循环持续读取传输帧，不等待上层业务消费或审批回调，保障控制信号始终畅通；入站缓冲通道容量必须覆盖有效结果信用额度与控制名额之和（至少为 `initialCreditWindow + maxControlFrames + 64`），保证控制消息不因流元素积压而阻塞，且合法结果生产不因容量瓶颈被误判为连接损坏。未知请求主动回发 `UnsupportedRequest`，未知通知仅在 `optionalNotification=true` 时可安全忽略，未知的必需通知直接报错。连接关闭区分调用方有限等待与内部工作实际结束：`CloseAsync` 使用统一的整体等待预算（涵盖排空出站写入与等待连接彻底关闭的总时长，超时直接返回避免阻塞调用方），内部收尾继续由连接持有并在后台执行；出站队列提供状态驱动的真实退出信号（覆盖已接纳生产者、待写帧、取消工作和写循环），连接在完成 `_closedTcs` 前汇聚等待真实退出信号，严禁用有限返回的 `DisposeAsync` 代替实际退出信号；汇聚等待中观察到的出站取消等收尾异常必须可靠记录到 `CleanupFailure`，保留原终止原因。连接启动通过启动屏障确保所有循环任务引用在执行 I/O 或触发终止前完全登记，生命周期锁内仅更新状态与引用；统一终止逻辑中，未决请求与待写帧的失败通知优先立即执行，绝不依赖可能阻塞的外部同步取消回调先返回；出站队列将接纳检查、生产者所有权登记与 `Stop` 纳入同锁裁决，彻底杜绝通过检查后迟到登记或访问已释放的 CTS 与信号量；`Stop` 在同一次同步裁决中原子确立停止状态与唯一取消工作所有权，重复 `Stop` 与 `Dispose` 观察同一个真实取消完成信号，取消回调在锁外异步执行，严禁依靠吞掉 `ObjectDisposedException` 掩盖释放竞态；出站队列 `DisposeAsync` 对在途生产者、待写帧、取消任务与写循环施加统一有限等待预算（2 秒），调用方超时直接返回避免死锁，内部继续在后台持有观察直至所有实际使用者、取消任务与写循环完全物理退出后才释放 CTS 与同步原语，严禁用提前释放解决挂起；`IpcConnection` 的连接取消任务优先于 `_stream.Dispose()` 启动，确保流释放等待不阻断取消任务解除读写阻塞；读写循环退出时不自我等待；底层流与内部同步原语严格在所有循环任务、取消任务与外部实际使用者物理退出后释放。直接编码业务载荷数据（模型或 DTO）的快捷接口与通用信封编码遵守相同的必需字段规则；文本补参入站原始 Token 提取与 JSON 反序列化最终生效字段规则严格一致（覆盖重复属性、大小写变体和转义属性名），并一致覆盖直接帧、`ChildMessage` 与 `ChildMessageReply`。

### 出站使用者与实际退出

出站队列在同一个状态锁内检查是否停止并登记生产者。登记成功的生产者持有队列使用权，直到名额等待、编码、帧完成等待和调用方取消注册清理均退出后才归还。停止后拒绝新生产者；最后一个生产者及待写帧退出时完成使用者归零信号。

队列的实际退出信号同时等待使用者归零、取消工作结束和写循环退出。未启动写循环时，由停止方排空残留帧并确认该路径结束；已登记的写循环必须执行完本地取消注册清理才报告退出。连接在这些工作结束后完成 `WaitClosedAsync`，公开的有限关闭和释放等待仍各自遵守原预算。队列释放超时后继续持有实际清理任务，以状态通知等待退出，不轮询计数。

出站取消异常由连接汇聚并记录到 `CleanupFailure`，不改变原终止原因。并发记录保留首个清理异常。行为检查须包含编码转换器受阻、生产者登记与停止竞争、取消回调抛错，以及重复文本字段在直接帧和两类子路由包装中的大小判定。

## 四、Schema 支持范围

校验器支持布尔 Schema，以及 `type`、`enum`、`const`、`properties`、`required`、`additionalProperties`、`items`、`minItems`、`maxItems`、`minLength`、`maxLength`、`pattern`、`minimum`、`maximum`、`exclusiveMinimum`、`exclusiveMaximum`、`multipleOf`。`$schema`、`$id`、`title`、`description`、`default`、`examples`、`format`、`$comment` 作为注解；`format` 在本支持范围内不承担断言。其他关键字明确报告不受支持。

解析按关键字分派：`Parse` 负责深度、布尔 Schema 与对象检查，随后逐个关键字写入解析期规则容器——受支持关键字各有读取步骤，注解关键字直接跳过，其余关键字报告不受支持；全部关键字读取完成后一次性构建不可变的规则节点。关键字不通过注册表或插件扩展，支持范围仍是本节的固定集合。数值约束在解析期按精确十进制表示读取，超范围即拒绝解析。

解析时检查字段类型、范围及重复项。`type` 数组非空且元素唯一；`required` 元素唯一；数量约束为可表示的非负整数；`multipleOf` 大于零。正则使用 .NET 正则语法，解析时验证语法并设置匹配期限，实例匹配超时报告校验未完成。

数值求值采用精确十进制表示；相等、整数和倍数判断共用同一实现。十进制指数绝对值的支持上限为 1000；定义超出求值范围时拒绝解析，实例求值超范围时报告校验未完成。缓存、深度和求值资源均有界，达到限制时明确失败。

校验失败信息包含路径、关键字和固定原因，避免带出实例值或外部原文。两端各在自身进程解析和复用规则。相关验收见 [阶段二验收](verification/phase-2.md)。
