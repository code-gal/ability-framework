# Ability Framework 工程经验与边界

本文积累智能体开发与软件工程实践中值得复用的经验。每条经验说明原因及适用范围；随着新证据合并、修正或删除。经验形成产品约束时，更新所属规格。阶段事实和验收结论见 [acceptance.md](acceptance.md)，工作安排见 [plan.md](plan.md)。

## 规格与表达

同一规则在多个文档复写后容易产生分歧。总规格建立概念和不变量，架构解释模块协作，项目规格定义实施契约，验收目录保存证据。写作时先确定内容的所属文档，再通过链接关联。

经验记忆提炼能够改善下一轮工作的判断，不累积执行流水。记录阶段完成比例或命令结果时，使用阶段验收文件；记录反复发生的问题时，保留成因、处理方法和适用边界。

文档先解释概念及其关系，再给必要的约束。短句须交代动作主体、对象和结果，避免靠抽象词和大量否定句省略解释。目录改名后，链接检查同时核对存在性与实际大小写。

## 设计与实施

模块拆分应明确状态所有权及变化原因。仅移动字段或按行数切片，容易继续保留隐含耦合。组件组合时传入实际所需的依赖，公开 API 保持可直接使用。

取消通常只结束等待，内部帧或资源可能仍在运行。容量和释放责任应随实际对象寿命管理，尤其适用于队列、子调用和异步收尾。

迁移或改名应按语义核对。公开 API 名称、线协议字符串、类型标识和诊断来源具有不同用途；大范围替换可能破坏插值表达式或兼容性。先检查差异，再验证受影响入口。

内部源生成序列化上下文保持 `internal` 时，对外门面可通过动态解析提供泛型消息体读取方法，既对调用方隐藏私有元数据，又避免跨程序集传递未公开类型。

有界资源校验（如数值指数上限、正则超时）遇到计算能力边界时，须明确报告“校验未完成”而非判定为“数据违规”，避免在未完成实际核验前对实例下达缺乏依据的结论。

## 验证成本与证据

XML 文档生成无警告并不证明注释充分。审阅公开 API 时还须核对参数、返回值、所有权和失败含义；阶段记录应分别报告编译结果与注释审阅结果。快捷编码路径也须遵守通用编码的必需字段规则，优化字节构造时同步核对输入检查。

保持行为的代码迁移优先使用源码对照、编译和白盒审计，运行验证集中在迁移完成后。新模块或新增功能才按新增风险安排必要的定向测试；职责提取或类型改名本身不构成重复整套测试的理由。编译成功和空测试发现只说明工程接线，行为结论需要真实调用及有效断言。

命令受环境权限阻止时，保留首个明确错误并核实具体权限，避免将固定失败反复扩面或直接归因于代码。耗时操作保持增量输出，期限参考实测，工具等待量级与产品运行策略分别管理。

受限文件沙箱会拒绝打开命名管道，`dotnet build` 因此在 Csc 任务上报 MSB3883 和 `\\.\pipe\LOCAL\dotnet_*` 访问被拒。这与被构建的代码无关：未改动的项目同样失败。判断时先构建一个未改动项目做对照，再决定是否申请更宽权限，放宽后同一命令原样通过。同一环境下 VSTest 宿主也不可用，testhost 启动时以 `EnableRaisingEvents` 打开父进程句柄被拒（Win32 5），`dotnet test` 中止。需要运行测试时改用进程内运行器 `dotnet run --project <测试项目> --property:EnableMSTestRunner=true`，不必修改工程文件。

业务文件的简单测试只模拟当前方法的直接需求。模拟宿主控制输入、审批与结果交互，适配器真实 I/O 由实际部件决定。以后引入外部操作样本时，由宿主提供 JSON，Sdk 通过业务方类型元数据解码，保持项目依赖方向。
