# Ability Framework 总规格

## 一、用途与规格体系

Ability Framework 提供宿主与文件技能之间的通信、接入和调用管理能力。宿主应用通过框架控制调用，文件技能通过框架接收输入、执行业务并返回结果。

全局业务组织规则以[文件切片与角色协作架构规约](../../../Docs/文件切片与角色协作架构规约.md)为准；接入和通信语义以[技能接入协议与 SDK 方案](../../../Docs/技能接入协议与SDK方案.md)为准。项目规格引用这些规则，补充组件、接口和具体实现约束。

## 二、核心术语

| 术语 | 含义 |
| --- | --- |
| Ability／文件技能 | 按文件切片规约组织、可组合的业务实现，包括模型、角色、流程和入口 |
| Launcher | 文件技能的进程入口，同一种入口可作为根调用或子调用 |
| 宿主应用 | 发起任务并提供交互、审批和策略决策的应用；Hosting 是其执行组件 |
| 任务（Task） | 围绕一个业务目标展开的执行，以 `TaskId` 标识；可包含多个调用 |
| 调用（Invocation） | 一次 Launcher 执行；内部调用键标识本次执行及其父子关系 |
| 调用会话（Session） | Sdk 为一次调用建立的本地运行对象，持有连接和能力组件 |
| 连接（Connection） | 一对上下游之间的通信实例，独立维护收发与请求匹配状态 |
| 请求（Request） | 需要答复的一次通信交互，以连接内的 `id` 匹配答复 |
| 操作（Operation） | 登记后受策略管理的一项工作，以操作键关联策略、尝试和进度 |
| 尝试（Attempt） | 操作的一次实际执行；同一操作可在策略允许时进行多次尝试 |
| 执行环境 | 本次执行采用的取消、时间和进度条件，与通信会话分别管理 |
| 受管资源 | 由宿主治理规则划定、访问前需要取得授权或租约的资源 |

任务标识用于归属，调用键用于生命周期管理，请求编号用于答复匹配，操作键用于执行治理。各标识分别产生和使用，业务代码通过 Sdk 获取相应能力。

本规格范围为单次调用进程。驻留多轮会话及外部 I/O 模拟在具体需求形成后扩展，现有调用会话的含义保持为一次调用的本地运行对象。

## 三、环境与工程规范

框架面向 .NET 11，具体 SDK 由框架目录的 `global.json` 选择。构建属性限定在 `ability/framework` 内；在 `Directory.Build.props` 中全局配置 `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>` 严格编译约束，类库使用 `net11.0`、可空引用类型和隐式 using。Core 与 Sdk 启用裁剪及 Native AOT 兼容性分析。实际发布与平台支持按验收证据确认。

```text
ability/framework/
├── Ability.Framework.slnx
├── Directory.Build.props
├── src/      # Core、Sdk、Hosting 类库
├── test/     # MSTest 测试、测试辅助进程（auxiliary/）、注释检查工具及工程脚本（script/）
├── tool/     # 参考宿主、开发工具、Aspire AppHost
└── spec/     # 总规格、项目规格与验证目录
```

一般目录使用小写单数名称。项目、项目目录、程序集、命名空间和 C# 标识符采用 .NET 命名约定；`Directory.Build.props` 等约定文件使用工具要求的名称。路径引用必须匹配文件的实际大小写，以 `/` 表达跨平台相对路径。

- **测试与断言集中**：`test` 目录存放测试项目、测试辅助进程、静态检查工具及工程验证脚本。可重复的行为断言集中在现有 `Ability.Framework.Tests` 项目中，使用已有 MSTest 框架编写；测试辅助进程（如 `MinimalLauncher` 与 `MinimalHost`）保留在 `test/auxiliary/`，作为跨进程测试辅助端点；基于 Roslyn 语法分析的注释与规模静态检查工具置于 `test/Ability.CommentChecker`；工程静态检查与自动化验证脚本统一归入 `test/script/`，并配备 `README.md` 用法说明。
- **工具与脚本规范**：`tool` 目录存放参考宿主、Aspire 和独立开发辅助工具。PowerShell 负责构建、启动、环境准备和结果收集，严禁在临时脚本中形成另一套协议测试实现。工程静态检查脚本与开发验证脚本统一收敛在 `test/script/`。
- **依赖隔离**：生产依赖为 Hosting → Core、Sdk → Core。宿主只需接入 Hosting，文件技能及其组合入口只需接入 Sdk。测试和开发工具通过正式项目引用复用实现，生产项目的构建与运行独立于它们。

所有手写类型及成员均须有中文 XML 注释，覆盖所有访问级别，包括嵌套类型、枚举值、构造函数、字段、属性、方法和事件。类型说明职责；成员按适用情况说明参数、返回值、取消、所有权及调用方需要处理的异常。记录类型的位置参数也须说明含义。语法检查工具仅能核查语法节点上是否存在对应文档注释，不代表注释内容的专业性免于人工审阅。

关键判断和较抽象的实现须解释设计意图，尤其是状态转换、并发同步、容量归还、资源移交及算法约束。注释描述当前行为，避免逐句复述代码。较长文件可用少量具名 `#region` 组织完整职责，方便人工折叠阅读。

项目采用规模预算降低人的认知负荷和 AI 阅读所需的上下文，保持单一职责，促进合适的机制复用，并便于测试与调试。手写 C# 文件不超过 1000 行，超过 500 行须审查职责、状态归属和依赖；函数控制在 100 行以内，超过 50 行须审查流程及设计。数字只是工程检查，职责和阅读成本须另行判断。不得为达标截断完整职责、制造参数袋或无必要的接口。

文件统计包含 XML 注释、空行和普通注释。函数统计采用从声明签名到结束的物理跨度，包含空行与主体注释，不计前置 XML 文档；方法、构造函数、访问器、局部函数和块体匿名函数均纳入，外层函数仍计入其内部声明的完整跨度，主构造函数参数不使整个类主体被计为函数。私有步骤函数及分部切片可以组织内聚实现，但不能仅以拆分宣称架构优化完成。生成代码按生成来源管理。既有生产代码在 [2.4.2](verification/phase-2.4.2.md)落实这套函数预算；测试及工具保留既有证据，新增或修改函数按同一准则审查，未修改的大函数记录规模，不因此启动测试体系重写。

文件与函数统计由 `test/Ability.CommentChecker` 用同一套 Roslyn 解析实现，`test/script/check_lines.ps1` 是唯一入口命令：一次运行输出全部手写文件的行数、函数身份（所属类型与成员）、起止行和跨度、按项目与子目录汇总的责任组规模，以及超限与待审查清单。`src` 生产函数超过 100 行判为不通过，测试与工具中的超限项只记录规模。

## 四、业务不变量

以下条件在正常执行、并发、取消和故障路径下都须成立。

- **类型与依赖独立。** 框架处理业务 JSON、资源引用和调用方提供的类型元数据。文件技能的业务类型始终由业务程序集定义，宿主接口可在只引用 Hosting 时使用。
- **通信状态按连接隔离。** 一条连接的编号、等待者和额度只属于该连接；转发组件维护明确的内外关联，答复只结束对应请求。
- **可变状态有唯一管理者。** Core 管理通信状态，Sdk 管理本地执行状态，Hosting 管理权威进程与资源归属。跨组件通过操作接口协作，资源移交同时确定释放责任。
- **业务执行与治理分别成立。** 宿主裁决访问和运行策略，业务适配器执行实际 I/O。登记或授权成功仅表示满足治理条件，业务结果仍由实际操作确认。
- **结束状态有明确含义。** 结果已提交、进程已退出和资源已回收是不同事实。调用完成的判定须包含其负责的收尾，故障报告保留原原因与实际已发生的结果。
- **容量与生命周期可核对。** 队列、缓存及等待者有明确上限和释放条件；取消结束调用方等待后，仍由资源所有者管理尚未结束的内部工作。
- **验证结果有证据。** 未执行、受阻、尚未完成校验和已通过分别记录。构建、行为、平台及发布验证各自说明覆盖范围。

公共契约变化先评估调用方与通信对端的影响。公开 API 的兼容性和线协议的兼容性分别管理，组件重组保持已确认的对外含义。
